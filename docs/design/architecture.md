# Architecture

## Package Boundaries

`@codeperfect/eslint-plugin` publishes a narrow public surface:

- named `codeperfectPlugin`
- first-party presets implemented in `src/infrastructure/presets.ts`
- package-owned rules through the public plugin object's `rules` map, assembled in `src/infrastructure/codeperfect-plugin.ts`

The package does not own a shared-config composition layer. Local repository lint configuration stays in `eslint.config.ts`.

## Source Layout

- `src/index.ts` is the public entrypoint used for package exports and API documentation generation.
- `src/domain/` contains the concrete rule implementations and domain-only support code.
- `src/infrastructure/` contains ESLint-facing adapters such as the plugin rule map and ready-to-use presets.
- `eslint.config.ts` owns the repository-specific architecture overlay, including the `boundaries` layer rules.
- `docs/rules/` contains curated rule reference pages.

## Documentation Layout

- `docs/design/` is reserved for curated architecture and maintenance documentation.
- `docs/api/` is reserved for autogenerated API output.
- `docs/rules/` remains curated rule reference content and is not overwritten by the docs generation command.

## Unused Member Analysis

A TypeScript Program is the compiler's snapshot of source files; its checker
resolves references to declarations and types. An analysis scope selects eligible
production files inside one configured API folder.

- `src/domain/architecture/program-analysis/` owns shared syntax catalogs,
  native reference-symbol lookups, and lazy module/triple-slash dependency edges.
  Both unused-code rules reuse these facts without sharing file classifications.
  Global scripts and augmentations remain conservative dependency roots.
- The member rule's domain-owned scope index resolves eligible API entries and
  their exact parent folders using the linted file's effective options.
- Production usage indexes are partitioned by owner before resolving consumer
  symbols and call signatures. Heritage indexes use the same eligible files;
  local forwarding and factory-return traversal enforce source-file membership
  at each recursive step.
- A transient reverse-dependency index selects eager reference consumers for
  each declared member name, including same-file and owner-local global or
  augmentation sources. Cycles use a visited set, not recursive expansion.
  Disconnected references remain available for structural and deferred symbol
  identity checks; dependencies outside the owner are not traversed for consumers.
  Whole-object operations and adapter inputs retain the full eligible owner scope.
- Observed imports are retained regardless of folder direction. Folder labels and
  architecture permissions do not prove that a consumer is absent.
- Operation catalogs remain syntax-only until candidates survive reference and
  adapter checks. Each scope lazily classifies operations, then evaluates pending
  candidates in operation-first batches, removing consumed members from later
  work. Completed positive and negative answers use declaration-keyed weak sets,
  not a retained operation-by-member result matrix.
- Node types, contextual types (including absent contexts), and property lists
  are shared within a type checker, never between replacement semantic snapshots.
  Member-specific identity and contract checks remain distinct.
- Immutable function catalogs separate own calls/returns from nested closure
  calls, preserving each sink's existing traversal semantics. Scope-owned
  parameter summaries distinguish standard JSON serialization from opaque
  request bodies; factory results additionally distinguish candidate declarations.
- Local flow uses iterative graph discovery and strongly connected components:
  mutually reachable parameter/return states form one group. Groups complete
  callee-first; a consumed exit marks the whole group used, otherwise it completes
  negative. In-progress visits are never cached as negative results. Predecessor
  edges are discarded after grouping; each completed group drops its graph
  records immediately. Remaining work queues leave scope when the query returns;
  only reusable syntax facts and weakly owned completed answers remain.
- The optional Angular adapter receives only that owner's production files.
  Public API exemptions remain separate from consumer scope.
- Nested API exposure is queried only for remaining candidates. Lazy type
  traversal checks declaration identity and stops on a match instead of
  collecting an export's entire type graph. Completed answers distinguish the
  program, candidate, API location, and remaining depth; traversal-local queues
  leave scope with the query. The existing six-level type budget is retained,
  with depth-neutral union/intersection edges.
- A conservative declaration-reference graph plus visible generic arguments
  rejects unrelated closed type branches before recursive instantiation.
  Declaration cycles use completed SCC results. Captured parameters, unavailable
  substitutions, and ambient augmentation uncertainty retain semantic traversal;
  syntax references alone never establish an API exemption.
- `no-unused-exports` retains its existing consumer analysis and runs independently
  of the member rule.
  Dependency edges do not themselves count as concrete export consumption.

### Cache Ownership

Cache owners define when facts may be reused and when the garbage collector can
release them. Weak keys permit collection after callers release the owner; they
do not force collection or detach TypeScript's own trees.

| Owner                                              | Retained facts and limits                                                                                                                                                                                                                                                                                       |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Most recently cached Program, held weakly          | Option-dependent API/scope indexes and production-usage buckets. Switching Programs evicts the previous entries even if that Program remains alive. Each named cache replaces its previous configuration rather than retaining option history.                                                                  |
| Analysis scope, held weakly                        | Production usage and heritage indexes, lazy operation summaries, completed parameter-flow answers, and candidate-specific factory answers. Production indexes use scope objects as weak keys, not historical folder names.                                                                                      |
| Program or checker, held weakly                    | Native reference symbols and dependencies, node/contextual types, properties, resolved call facts, and candidate API/relevance answers. These facts never cross replacement semantic snapshots; nested node/type/candidate keys are weak. Source-reachability results are bounded to 16 source roots per owner. |
| Immutable syntax node, held weakly                 | Shared file and function catalogs containing syntax facts only; these may survive syntax reuse across Programs without preserving old semantic answers.                                                                                                                                                         |
| Angular checker and template metadata, held weakly | Component metadata is checker-specific even when class syntax is reused. Parsed nodes follow the immutable metadata object. A replacement checker rereads external templates and creates a new parse snapshot.                                                                                                  |

Completed operation and flow answers do not retain an operation-by-candidate
matrix or temporary discovery/grouping queues. API type answers distinguish
remaining depth, with at most seven depth entries (zero through six) per
type/location/candidate combination.

Scope or configuration replacement makes obsolete analysis collectible unless
callers still hold it. Releasing a Program also permits its checker-owned facts
to be collected, but syntax snapshots or native type graphs still held by
TypeScript, parser services, or other callers remain outside plugin ownership.
The export rule retains its independent Program-weak index.

### Measured Performance

The reference workload completes with both unused-code rules under Node's
default heap and explicit `--max-old-space-size=4096`. The measurements below
satisfy the [approved benchmark contract](../../.specs/SPEC.md#benchmark-setup);
they are observations for these inputs, not timeouts or memory ceilings enforced
by the rules.

**Environment and inputs.** Measured on 2026-11-12 using Windows 11 Pro
10.0.26200, Ryzen 9 9950X (16 cores / 32 logical processors), approximately
61.7 GiB physical memory, Node v24.18.0, ESLint 10.14.0, TypeScript 6.0.3,
typescript-eslint 8.72.2, and `@codeperfect/eslint-config` 2.7.0. The local
reference project contains four independent package API folders. Healthy data
contains 265 tracked TypeScript files, including tests and tooling. Recursive
data adds an eight-way generic builder fixture exposed through one package API.
The host is shared; CPU scheduling is not isolated and filesystem caches are
not cleared.

Each result is the median of three fresh sequential Node processes, including
startup and exit. Existing typed ESLint configuration and other rules remain
enabled, with `projectService: true`, no result cache, no lint concurrency, and
`NODE_OPTIONS` unset. Memory columns are maxima across each row's three runs.
Used heap is observed garbage-collection/phase high water, not a continuous peak.
RSS is resident process memory, measured separately using Windows peak working
set and Node's maximum RSS. One GiB is 1,073,741,824 bytes.

| Dataset   | Heap     | Three wall times (seconds) | Median seconds | Observed heap GiB | Peak RSS GiB |
| --------- | -------- | -------------------------- | -------------: | ----------------: | -----------: |
| Healthy   | Default  | 21.332 / 21.281 / 21.176   |         21.281 |             2.921 |        3.343 |
| Healthy   | 4096 MiB | 21.336 / 21.401 / 21.152   |         21.336 |             2.896 |        3.314 |
| Recursive | Default  | 21.140 / 21.402 / 21.547   |         21.402 |             2.893 |        3.319 |

The unchanged project also completed before optimization; its original reported
crash was not reproduced. The synthetic recursive workload did exhaust the heap
in both installed and pre-optimization source member-rule runs, including the
explicit 4096 MiB source run. Those crashed runs have no completed diagnostic
array. They establish a reproducible type-expansion regression, not the exact
cause of the originally reported crash.

**Correctness and controls.** All 46 cold-process measurements complete:
34 combined/export-only/member-only/both-disabled matrix runs and 12 matched
compiled export controls. Completed baseline diagnostic arrays match directly,
not just by count. Healthy combined analysis retains 52 existing errors and
recursive combined analysis retains 53; neither has target-rule, fatal, or warning
findings. The recursive fixture adds only its sorting error; excluding that file
leaves the exact original healthy combined array. Export-only and both-disabled
diagnostics match their respective original baselines. Additional findings when
the member rule is disabled are nine existing unused disable directives.

Source export-only default/4096 MiB medians are 20.823/20.766 seconds for healthy
data and 20.860/20.725 seconds for recursive data. Installed default-heap medians
are 19.615 and 19.659 seconds, but source and installed loaders differ.
Matched controls preload both built plugins identically, retain other candidate
rules, and swap only the export implementation. Baseline/candidate medians are
22.329/22.176 seconds for healthy data and 22.124/22.184 seconds for recursive
data, with overlapping ranges and exact export diagnostics. This does not prove
zero overhead or statistical equivalence on every workload.

Two additional processes each perform six full lint passes, alternating the
original effective options with an added nonmatching test glob and restoring
the original options. All 12 passes retain exact combined diagnostics without
result caching. Repeated/restored `lintFiles` calls take 5.099-5.884 seconds;
these exclude startup and explicit harness setup, include lazy ESLint work
inside the calls, and are not cold-process acceptance medians.

**Ownership limits.** A separate forced-GC probe warms native scope, syntax,
reference, API, and type facts through eight outer/nested configurations. With
the Program alive, only its current observed scope/index remains; after external
owners are released, the observed Program, checker, scopes, and indexes collect.
The small fixture catalogs operations but does not execute flow summaries or the
full Linter. Its roughly 74.8 MB live-Program versus 29.9 MB released-Program heap
samples demonstrate ownership, not a production memory-reduction guarantee.
TypeScript/parser-owned graphs remain outside plugin control.

**Provenance and local evidence.** The measured source snapshot is
`28853bf8d3b135f4bc2bf1f1411a33efa58b1d6bb655e854caae5238c6a27e84`;
all 318 source files match it. Healthy and recursive dataset hashes are
`91fa56129f682b10e16eac3880c5fa15c2dd35cb9217fc2eec0659d8fa6eb59e` and
`c39cbb0605ea399a5e6e90d908174541f55d8b43248530739b60ae149c959895`.
The original runner and fixture are unchanged. The worker's only historical
change corrects source inventories to include untracked, nonignored files;
reversing that exact change reproduces its original checksum. Original and
corrected inventories agree for this final source; loader and timing/GC protocol
are unchanged.

Local, untracked evidence is retained in
`logs/member-benchmark/proof-20261112-111458/`: `manifest.json` identifies every

The measured implementation passed `npm run validate`: all 11 stages, including

## Maintenance Expectations

- Keep the README focused on install, usage, exports, and links into this docs tree.
- When the exported surface changes, regenerate `docs/api/` and review the design docs for drift.
- When a rule is added or renamed, update `docs/rules/`, the plugin rule map, preset selections, and any published references together.
