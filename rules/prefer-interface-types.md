# `codeperfect/prefer-interface-types`

## Summary

Prefer named interfaces or type aliases over inline object types in type positions.

## Enabled by

- `typescript`
- internal `codeperfect` plugin registry

## Why this rule exists

Named types improve readability, reuse, and documentation quality. Inline object shapes in signatures are harder to reference, extend, and evolve over time.

## Rule Details

- Inline object types are disallowed in:
  - function parameters
  - function return types
  - variable type annotations
- Instead, define a named:
  - `interface`, or
  - `type` alias

### Allowed

- Named interfaces or type aliases
- Inline object types in:
  - generic constraints
  - mapped or utility types

### Exceptions

Inline object types are allowed when:

- used in generic constraints

  ```typescript
  function process<T extends { id: string }>(input: T): T {
    return input;
  }
  ```

- used with utility or mapped types

  ```typescript
  type PartialUser = Partial<{ id: string; name: string }>;
  ```

## Autofix

The rule can replace every reported inline object type with a generated top-level interface. Generated interfaces are appended as one block at the end of the file, and each one is preceded by this review marker:

```typescript
// TODO: Review this autogenerated type name
interface Input {
  value: string;
}
```

Generated names use PascalCase without adding an `I` prefix or a `Type` suffix:

- Parameters use their identifier, such as `input` becoming `Input`.
- Destructured or otherwise unsupported parameters use `Parameter`.
- Variables and return types use the nearest declared variable, function, or method identifier.
- Anonymous contexts without an identifier use `Type`.
- Existing top-level import, value, and type names are reserved. Collisions receive numeric suffixes such as `Input1` and `Input2`.
- Equal object shapes generate separate interfaces; the fixer does not deduplicate them.

The rule keeps reporting without an autofix when moving a type to module scope could change its meaning. This includes types that depend on function, class, or namespace scope, contextual `this` types, and declarations inside namespaces or ambient modules. Names declared in inner scopes are also reserved so a local declaration cannot capture a generated type reference.

For union, intersection, and parenthesized wrappers, one inline literal is reported per lint pass. ESLint's normal iterative autofix processing fixes later literals on subsequent passes.

## Invalid

```typescript
function saveUser(user: { id: string; name: string }) {}
```

```typescript
function demo(input: { value: string }): { value: string } {
  return input;
}
```

```typescript
const handler: (input: { value: string }) => void = () => {};
```

## Valid

### Using interfaces

```typescript
interface UserInput {
  id: string;
  name: string;
}

function saveUser(user: UserInput) {}
```

```typescript
interface DemoInput {
  value: string;
}

function demo(input: DemoInput): DemoInput {
  return input;
}
```

### Using type aliases

```typescript
type DemoInput = { value: string };

const demo = (...values: DemoInput[]): DemoInput => values[0]!;
```

```typescript
type SaveUserInput = { id: string; name: string };

function saveUser(user: SaveUserInput): void {}
```

```typescript
// generic constraint
function process<T extends { id: string }>(input: T): T {
  return input;
}
```

```typescript
// utility type
type PartialUser = Partial<{ id: string; name: string }>;
```
